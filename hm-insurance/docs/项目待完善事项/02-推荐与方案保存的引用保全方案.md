# 推荐与方案保存的引用保全方案（待实现）

当前已按现有代码风格完成简化修复：沿用 `additional_info` 自定义事件和按消息保存的检查点数据，不增加工具 artifact 协议、模型来源参数或数据库字段。

- 候选查询发送 `candidate_products`，保存成功发送 `plan_items`，拒绝不发送保存结果。
- 条款编号由产品 ID、父块 ID 和内容生成，避免多次查询重名；本轮事件按产品和来源合并。
- 后续回答从历史附加信息补齐正文实际引用的来源，保存恢复后仍能显示引用。
- 前端同时解析产品与来源并去重，流式结束后直接使用 SSE 补发的信息，不重载整段历史，避免卸载产品图片导致滚动跳动。
- 条款事件统一使用 `sources` 字段，不兼容旧版裸来源字典，也不按编号前缀分支处理。

已通过后端回归（含父子图检查点中断恢复）、前端构建和来源合并检查；尚未进行真实模型、PostgreSQL 和浏览器联调。以下根因表描述修复前行为，后续完整设计保留作为扩展方向。方案脱离会话后的独立证据快照、金额校验及断流前来源可靠落盘仍待完善。

## 现象与根因

截图中正文保留了 `[ref-001]`、`[ref-003]`，但没有转换成可点开的引用。当前前端只有在**当前消息的附加信息**中找到对应来源时才生成引用按钮。文字中的编号存在，不代表原文已传递或保存。

| 位置 | 当前行为 | 后果 |
| --- | --- | --- |
| `agents/tools.py::query_candidate_products` | 只返回产品列表给模型，不发送 `additional_info`；提示词明确不为此类数据生成引用 | 候选产品卡片没有工具事件；产品概览也没有可追溯的来源标识 |
| `agents/tools.py::query_product_clause` | 每次调用都从 `ref-001` 编号，没有携带父块 ID | 同一轮查多个产品时编号冲突，跨轮不能可靠识别原文 |
| `modules/chat/service.py::chat_stream` | 每次来源事件直接覆盖本轮 `additional_info`，结束只绑定最后一个 AI 消息 ID | 多次检索仅最后一次被写入消息来源；实时前端和刷新后的历史可能不一致 |
| `agents/tools.py::save_insurance_plan` | 确认载荷仅有方案数据；成功返回 ID、状态和提示语，不发送来源或方案项事件 | 恢复请求的来源变量为空；模型即使复述历史编号，新回复也没有对应原文 |
| `modules/insurance_plan/models.py`、`repository.py` | 保存方案与产品 ID、理由、预算，没有证据快照 | 聊天检查点不能替代方案自身的证据存档 |
| `frontend/src/additionalInfo.ts` | 多字段对象命中来源后直接返回；事件挂到最后一条 assistant | 后续同时发送产品和来源时会丢产品；无法准确对应多条 AI 消息 |

保存回复是否确实复用了哪次检索的编号，需要运行日志才能判断；上述数据断点可以直接从代码确认。单纯改提示词或让前端全局寻找 `ref-001` 都无法可靠解决，后者还可能把不同产品的条款关联错。

## 推荐设计

### 1. 区分产品概览与条款证据

保留现有 `additional_info` SSE 事件名称，统一内部结构，允许同时携带：

- `schema_version`、`message_id`：协议版本与回答归属。
- `candidate_products` / `plan_items`：用于产品卡片和保存回执。
- `sources`：按稳定 ID 索引，包含 `kind`、`product_id`、来源定位、原文/数据快照。

产品概览来源使用 `kind=product`，保存产品 ID、查询时的产品字段及快照时间/版本；可核对名称、保险公司、最低保费等。条款来源使用 `kind=clause`，保存产品 ID、父块 ID、条款名称、章节路径、内容版本/哈希与原文。前端分别显示产品资料和条款详情，产品简介不能证明续保或免责结论。

候选查询和条款查询须把相同来源 ID 同时返回模型、注册到服务端状态、发送前端。不能只补一个前端事件。

### 2. 稳定编号与按消息绑定

建议使用 `clause-<product_id>-<parent_chunk_id>-<content_hash>`，产品资料使用 `product-<product_id>-<snapshot_hash>`；界面仍按引用顺序显示 `[1]`、`[2]`。不同产品和不同版本不共用同一来源 ID。

在 Graph 状态维护来源注册表，子 Agent 和父 Graph 明确共享/传递此状态。按稳定 ID 合并，保留跨轮复用所需的数据；自定义流事件只用于通知前端，不能作为唯一存档。需在实现时验证子图写入如何同步父图，以及中断恢复时的检查点命名空间。

每条可展示 AI 消息绑定自己的产品数据及来源子集。结束时解析实际使用的编号，从已注册证据中解析历史来源，校验产品归属和原文存在性；缺失时标记不可追溯，不凭编号补造原文。语义上是否支持结论仍需单独验证，ID 校验本身不代表事实校验。

本轮多次工具调用按类型和来源 ID 累积，不能覆盖；重复来源去重。SSE 文本与附加信息均带回答 ID，前端处理来源先于文本到达的情况。来源先写检查点再投递；历史接口返回同一结构及消息 ID，保证刷新后仍可打开。

### 3. 保存确认与证据快照

中断前在服务端生成待确认快照：方案版本、所选产品、展示金额及其含义、推荐理由、所用条款来源和引用关系。确认界面显示这个版本；批准恢复后使用同一快照保存，不能重新由模型拼装证据。新增来源字段应由服务端解析与校验，不要求模型提供可信原文。

在 `insurance_plans` 增加带版本的 `evidence_snapshot JSONB`，通过数据库迁移部署，与方案、方案项在同一事务写入。保留必要原文与产品数据，避免条款更新、检索重建或会话删除后无法追溯；不保存无关的整段对话或其他产品证据。

批准成功后发送 `plan_items`、`plan_id` 和该快照来源，供新回复引用；拒绝不写库、不发送成功回执。仅含“保存成功”的操作提示无需强行添加条款引用，但再次描述续保、免责等结论时必须携带对应来源。方案读取接口也应返回证据快照；当前 Python 模块尚未提供完整方案读取接口，需同步实际承接该接口的服务。

截图中还出现最低保费 `255元` 与保存后的 `254元档参考` 不一致：应一并通过确认快照校验产品和金额，避免保存回执重新生成事实。本方案不修改现有金额字段语义。

### 4. 兼容与降级

所有来源统一通过 `sources` 字段读取，不保留旧版裸来源字典的解析分支。已保存但没有原文的旧消息显示“来源暂不可用”，不能根据重名旧编号关联其他消息。更新后的提示词引用实际返回的 ID，并允许引用已注册且可核对的历史证据；不要继续使用含糊的局部编号。

## 落地顺序与验收

1. 优先修条款 ID 冲突、事件累积、消息绑定和历史来源解析；这直接解决截图中编号有文字却无法打开的问题。
2. 补候选产品事件与产品概览来源，同时更新前端分型解析。
3. 增加确认快照、方案证据迁移与保存回执事件，打通批准恢复和方案读取。

实现后至少验证：

- 同一轮查询两个产品、多次检索同一产品：原文不互相覆盖、不串产品。
- 下一轮不再检索而复用证据：引用仍可打开，刷新历史后结果一致。
- 发起保存、刷新确认界面、批准恢复：引用、产品和金额均与确认快照一致。
- 拒绝保存：无方案写入、无成功回执，原消息来源不丢失。
- 来源事件先于文本、多条 AI 消息、断流后重载：来源正确归属。
- 候选为空、条款检索为空、模型输出不存在的 ID、旧历史缺原文：明确降级，不生成伪引用。
- 条款更新或会话删除后读取已保存方案：仍能看到保存时的证据版本。

当前已有 `tests/test_chat_history.py` 只验证人工写入的来源能按消息恢复，没有覆盖流式收集、多工具冲突和保存后的跨轮复用；后续应补这些链路测试。新增 `tests/test_citation_stream.py` 覆盖查询合并、跨轮引用、来源编号及父子图中断恢复。
