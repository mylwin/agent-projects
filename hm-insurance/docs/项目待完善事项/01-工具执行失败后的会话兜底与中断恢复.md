# 01 工具执行失败后的会话兜底与中断恢复

> 记录日期：2026-11-14
> 状态：待完善。已修复本次保存代码异常并人工修复受影响会话；通用兜底、重试和中断恢复尚未实现。
> 涉及功能：保险顾问聊天、`save_insurance_plan` 工具、PostgreSQL checkpoint、SSE 输出。

## 问题现象

用户确认保存保险方案后，工具执行异常，聊天流中断。修复保存代码后，继续在同一会话发送消息，DeepSeek 仍然返回：

```text
400 Bad Request
An assistant message with 'tool_calls' must be followed by tool messages
responding to each 'tool_call_id'.
```

日志顶部的 `LangChainBetaWarning` 表示 v3 流式协议仍处于实验阶段，不是本次 400 的直接原因。

## 为什么修复保存代码后仍会报错

1. 模型返回带有 `tool_calls` 的 AI 消息，图运行时将其保存到 checkpoint。
2. `save_insurance_plan` 开始执行，发生异常后向外抛出。
3. 本次异常没有转换为对应调用 ID 的 `ToolMessage`，执行中断。
4. 下一轮使用相同 `thread_id`，恢复了不完整的消息历史，又追加新的用户消息。
5. 模型服务发现工具调用没有配套结果，在请求校验阶段返回 400；此次请求尚未执行保存工具。

因此存在两层问题：**业务工具为什么失败**，以及**失败后会话如何保持可继续执行**。只修复第一层，不会自动修正已经写入 checkpoint 的旧消息。

## 本次已定位和处理的原因

| 问题 | 原因 | 当前处理 |
| --- | --- | --- |
| Repository 初始化失败 | 数据操作类误继承 Pydantic `BaseModel`，给未声明字段 `session` 赋值时报错 | Repository 已改为普通类 |
| 保存方案时 `flush()` 失败 | `ForeignKey("users.id")` 无法在 SQLAlchemy metadata 中解析；本服务未定义并加载 User ORM 模型 | 方案 ORM 仅保存 `BigInteger` 用户 ID，与现有会话模型一致；数据库已有外键约束未修改 |
| 同一会话后续请求持续 400 | 前述失败留下没有对应 `ToolMessage` 的历史调用 | 通过 LangGraph 状态更新补充错误结果并创建新 checkpoint，保留原消息和旧检查点 |

本次先后定位到了不同的失败调用，说明修复一条历史调用后，后续新的工具异常仍可能再次产生不完整历史。

### 已完成的验证

- 应用和 Agent 能正常构建，相关 ORM 表依赖、外键解析与 INSERT 编译通过。
- 使用失败调用的原始参数验证方案保存路径，方案及 3 条产品项写入成功。
- 保存验证放在外层事务和保存点中，结束后全部回滚，并确认没有留下测试方案。
- 人工修复后检查消息顺序，当前受影响会话不存在缺失的工具响应。

以上不代表完成了自动恢复机制，也不代表已通过真实模型对话重新验证整个保存流程。

## 当前仍未完善的地方

- 工具执行异常会继续向图运行时抛出，目前没有统一的失败结果转换。
- 新对话输入前没有检查持久化消息中的工具调用与结果是否完整。
- SSE 没有针对这类异常提供业务错误事件、可恢复标识或恢复入口。
- 没有持久化的恢复流程；本次使用的临时修复脚本不在项目中，也不是线上兜底能力。
- 保存方案没有按工具调用或业务请求实现幂等，不能遇到失败就直接自动重跑。
- 目前只在工具描述中要求用户确认，尚无独立的后端确认状态校验。

## 后续可考虑的改进

以下均是待设计方向，本次没有新增中间件或实现这些功能。

### 1. 工具失败兜底

- 对预期的业务异常返回带有相同 `tool_call_id` 的错误 `ToolMessage`，让模型知道工具失败，保持消息协议完整。
- 工具返回失败或结果未确认时，禁止向用户宣称保存成功；日志保留排查依据，返回模型的内容不包含数据库连接信息或完整异常参数。
- 对无法继续执行的异常，明确结束本轮，向前端提供错误事件及后续处理提示，避免只留下突然断开的流。
- 多工具调用中保留已成功的结果，只处理缺失或失败的调用。

### 2. 失败中断后的恢复

- 在接受新输入或提供恢复入口时，检查 checkpoint 中的消息顺序、待执行任务和错误状态。
- 区分“已确认失败”“执行结果未确认”“业务已提交但响应未返回”，再决定如何继续。
- 可选择从失败步骤恢复，或在补齐真实的失败／未确认结果后进入新一轮；需要结合当时的任务状态选择，不能把两种方式混为一谈。
- 人工修复仅使用图状态接口创建新 checkpoint，保留原状态；不直接改 BYTEA、删除整段历史或伪造工具成功。
- 恢复前重新校验会话归属与当前用户上下文。

### 3. 写入操作的幂等与重试

- 为保存方案设计稳定的幂等标识，并通过业务唯一约束或执行记录查询结果。
- 对已成功提交但响应丢失的调用，返回原方案结果，避免生成重复方案。
- 查询类工具可考虑有界重试；保存类工具只有在能确认不会重复写入时才重试。
- 协调同一 thread 的正常聊天与恢复操作，避免两条执行同时覆盖状态。

## 后续验收清单

- [ ] 工具在执行前／执行中抛错后，当前会话能继续处理后续问题，不再产生缺失工具响应的 400。
- [ ] 一次 AI 消息包含多个工具调用时，成功结果保留，每个调用都有准确对应的结果。
- [ ] 数据库事务回滚后，界面明确提示保存失败，不出现虚假的保存成功信息。
- [ ] 数据库已提交但响应丢失时，重试或恢复不会重复创建方案。
- [ ] SSE 中断或客户端取消后，可以识别执行状态，并给出明确的继续或重新开始方式。
- [ ] 恢复操作校验会话归属，不误用其他用户上下文。
- [ ] 恢复保留原聊天内容和旧 checkpoint；不能可靠判断结果时明确标为未确认。
