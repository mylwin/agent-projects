## 1. 架构决策

如果由我现在开发，我会选择：**TypeScript + React + Vite 前端，Python + FastAPI 后端，LangChain 单 Planner Agent，PostgreSQL 保存业务与执行数据，高德提供国内地点、天气和路线能力。**

采用前后端分离的模块化单体。后端的 API、规划编排、工具适配和校验模块在同一应用中运行，通过清晰接口隔离职责。先完成生成、展示、修改、保存行程的完整闭环，再根据实际需求引入显式 LangGraph 工作流、RAG 和独立任务执行器。

选择 Python 后端，是为了沿用此前的 Agent 学习路线及其生态；React 使用 TypeScript 不要求后端也使用 TypeScript。前后端通过 OpenAPI 契约协作，无需为了统一语言增加第二套 Agent 内核。

当前已建立 uv 配置与目录骨架，并完成 React 前端原型。前端采用独立 CSS、Lucide 图标和文档中的 JSON 样本，已实现 React Router 计划列表/详情、独立对话、结果版本、侧栏收缩和本地示例调整；尚未接入真实模型、业务后端与高德服务。下文描述目标系统架构，架构图为设计示意，不代表整体能力已实现。前端现状与数据接入边界见 [01-interface-design.md](../02-frontend/02-design/01-interface-design.md) 和 [01-data-contract.md](../02-frontend/03-data/01-data-contract.md)。

## 2. 产品范围与设计前提

首版按以下假设设计，后续需求变化时重新评估：面向中文用户，支持全国国内目的地的一次单区域 1–5 天旅行，城市/区县/景区需解析和消歧；不设苏州白名单，多城市串游后续扩展。实际地点/路线覆盖依供应商验证，能力缺口需明确反馈。使用现有地图服务，不进行酒店、门票或交通票务交易。

| 能力 | 首版交付范围 |
| --- | --- |
| 需求输入 | 目的地、出行日期、人数、预算、出行节奏、兴趣偏好 |
| 生成行程 | 查询真实地点，按天组织活动、交通与预算估计 |
| 对话修改 | 例如“第二天下雨，改成室内”“保留博物馆，减少步行” |
| 展示 | 对话进度、每日行程卡片、地图地点与路线联动 |
| 保存 | 行程列表、详情与版本；修改后保留旧版本 |
| 异常反馈 | 缺信息时要求补充；接口失败或约束无法满足时说明原因 |

预算需要先定义口径：币种默认人民币，明确按人还是全团、是否包含往返大交通及住宿。未明确时显示假设或请求补充，不擅自把不同口径相加。

开放时间、天气及价格都可能缺失或过期。产品区分“已查询信息”“估计”“待核实”，不把生成成功等同于保证可出行。出行日期超出供应商预报范围时，不生成虚构的逐日天气。

首版以本地单用户为开发场景；开放给多个用户前增加登录、资源归属校验与调用额度。框架设计保留用户归属字段，但不先建设复杂权限平台。

## 3. 技术栈与选择理由

### 3.1 前端

| 层次 | 选择 | 用途与边界 |
| --- | --- | --- |
| 语言与视图 | TypeScript + React | 组件、页面及类型约束，开启 strict |
| 工程构建 | Vite + pnpm | 开发服务、静态构建、依赖锁定 |
| 路由 | React Router | 行程列表、规划工作台、行程详情 |
| 样式与基础组件 | Tailwind CSS + shadcn/ui | 表单、抽屉、对话框等；旅行卡片与地图联动自己实现 |
| 服务端数据 | TanStack Query | 行程查询、提交后的刷新、请求错误状态 |
| 局部交互状态 | React state / reducer | 选中日期、POI、流式消息、面板展开状态 |
| 表单 | React Hook Form + Zod | 日期、人数、预算及必填项的前端校验 |
| API 类型 | openapi-typescript | 从 FastAPI 的 OpenAPI 生成 TS 类型，减少两端字段漂移 |
| 地图 | 高德地图 JS API | 地点标记、路线和行程联动，封装为独立组件 |
| 测试 | Vitest + Testing Library；Playwright | 状态处理与关键用户流程 |

我选择 Vite SPA，是因为首版重点是登录后或个人使用的交互工作台，后端已经由 FastAPI 承担。若以后需要可被搜索引擎索引的目的地内容与公开分享页，再评估 React Router 的框架模式或 Next.js。这个选择是产品需求判断；React 官方对从零构建也明确提示了路由、数据加载和 SSR 等能力需自行组合的取舍。[React 官方说明](https://react.dev/learn/build-a-react-app-from-scratch)、[Vite 文档](https://vite.dev/guide/)

TanStack Query 只管理服务端数据缓存，选中景点等 UI 状态放在 React 中；SSE 的临时事件由运行状态 reducer 管理。首版先不增加全局状态库，避免同一份行程同时存于多处。[TanStack Query 概览](https://tanstack.com/query/latest/docs/framework/react/overview)

工作台建议由对话区、每日行程区、地图区组成。桌面端并排展示，窄屏以标签页切换。点击行程地点可聚焦地图，点击地图标记可定位到对应卡片；联动依赖稳定 POI ID，而不是地点名称字符串。

### 3.2 后端、Agent 与存储

| 层次 | 选择 | 用途与边界 |
| --- | --- | --- |
| Python 环境 | uv + pyproject.toml + uv.lock | 管理兼容的 Python 与依赖版本 |
| API | FastAPI + Uvicorn | REST、流式响应、OpenAPI、请求校验 |
| 数据结构 | Pydantic | 输入、模型草稿、业务行程和事件模型 |
| Agent | LangChain `create_agent` | 单 Planner 的模型—工具循环 |
| 外部请求 | HTTPX AsyncClient | 地图与天气查询，统一超时、错误和请求记录 |
| 数据库 | PostgreSQL | 行程、修订、会话消息、运行状态与工具摘要 |
| ORM 与迁移 | SQLAlchemy 2.x + Alembic | 仓储实现与数据库版本演进 |
| 开发检查 | Ruff + pytest | 静态检查、业务约束与集成测试 |
| 部署 | Docker Compose + Nginx | 前端静态资源、API 代理和 PostgreSQL |

这里的版本是技术路线，不是完整依赖锁定清单。真正初始化时选择相互兼容的发布版本，提交 `pnpm-lock.yaml`、`uv.lock`，不直接复制参考项目的旧版 LangChain 依赖。

PostgreSQL 从首版使用，是因为行程版本、运行状态与并发更新天然需要事务。开发环境也使用同一数据库类型，减少后续切换差异。结构化元数据放普通列，嵌套行程正文可以先放 JSONB；不必把每个活动立即拆成关系表。

### 3.3 模型与外部数据

主模型首选接入**阿里云百炼中国北京地域的 Qwen Plus 系列**，作为中文工具调用场景的起始基线；不以尚未实测的排名作为依据。官方能力表列出该地域支持 Function Calling 与结构化输出，其他地域不能据此类推。[模型能力表](https://help.aliyun.com/en/model-studio/qwen-plus)

模型、地域、超时和调用上限通过后端配置注入。集成时先验证流式输出、工具调用、工具错误回填、结构化返回，再选定可复现的模型版本并记录到每次运行中。若你已有可用的模型服务账户，可更换适配器；当前并未验证你的账户与额度。

原生结构化输出与工具调用同时使用需要实际模型支持。若组合不兼容，将“带工具收集信息”和“根据已有证据生成结构化行程”拆成两步；仍只保留一个 Planner，不为此引入多个独立 Agent。[LangChain 结构化输出](https://docs.langchain.com/oss/python/langchain/structured-output)

高德分两类接入：浏览器使用地图 JS SDK 展示，后端使用 Web 服务查询地点和路线。浏览器地图 key 与后端服务 key 分开管理；模型凭证与后端服务 key 只在服务端使用。JS API 的安全配置按官方方案实施。[高德 JS API 安全配置](https://lbs.amap.com/api/javascript-api-v2/guide/abc/jscode)

### 3.4 后续按需加入

| 组件 | 引入条件 |
| --- | --- |
| 显式 LangGraph StateGraph | 已确认需要业务分支、暂停恢复或阶段级重试 |
| pgvector | 有可维护的攻略知识源，并需要语义检索 |

首版不叠加 Deep Agents、pi-agent-core 或自研通用运行时，理由沿用框架选型文档。工具由 HTTP 适配器直接接入；接多个现成 MCP 服务时再评估 MCP。

## 4. 系统结构与职责

配套文件：[可交互架构图](03-diagrams/01-system-architecture.html)。图中后端模块属于同一应用，不代表独立微服务；浏览器地图展示与后端地图数据查询是两条独立路径。

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| React 工作台 | 表单、对话、地图、版本切换与错误反馈 | 工具执行、预算真实性判断、持有模型密钥 |
| API 层 | 参数校验、资源访问、运行入口、HTTP/SSE 协议 | 编写 Prompt、决定地点选择 |
| 规划应用服务 | 合并需求、加载行程、调用 Planner、触发校验与保存 | 地图供应商协议细节 |
| Planner Agent | 按需求查询必要信息、选择候选地点、输出草稿 | 直接写数据库、跳过规则校验 |
| 工具层 | 参数约束、调用领域服务、返回模型可用的有限结果 | 决定整个任务如何完成 |
| 领域服务与校验器 | 地点规范化、路线核验、预算汇总、行程约束 | 依赖聊天框架的内部消息格式 |
| 仓储层 | 查询、事务、版本更新及运行记录 | 执行模型循环 |

整体调用顺序：浏览器 → FastAPI → 规划应用服务 → Planner / 领域服务 → 校验器 → 仓储 → 浏览器。领域服务返回普通类型或 Pydantic 结构，使未来更换运行时不会迫使地图、预算和行程规则重写。

## 5. 一次生成或修改如何执行

1. **校验需求**：解析城市、日期、预算口径及偏好；缺少必要信息时结束本轮，返回待补充字段。
2. **创建运行记录**：生成 `run_id`，记录输入与目标 `base_revision`，检查是否已有活动运行。
3. **准备上下文**：读取当前行程及必要会话摘要，不把全部历史原样塞进 Prompt。
4. **运行 Planner**：允许查询地点、天气；需要时查询交通耗时。查询结果带来源与时间。
5. **接收结构化草稿**：模型输出候选 ID、活动安排和说明，不自行填造地点坐标。
6. **执行强制校验**：候选 ID、天数、重复活动、预算汇总及路线耗时均由程序检查。即使模型没调用路线工具，应用服务也检查最终选中地点间的必要路线。
7. **有限修复**：可修复问题返回结构化错误给 Planner，初始最多修复一次；总调用预算不因修复而重置。
8. **保存与返回**：通过校验后，以事务写入新版本并更新运行状态，再发出成功事件。无法满足时返回原因，保留已有有效行程。

初始可配置限制建议为：每次运行最多 8 次模型调用、12 次外部工具调用、120 秒总截止时间，单工具超时更短。这些是起步配置，不是已经验证的性能指标；重试、修复和结构化生成均计入同一预算。

只对可重试的查询错误做少量退避重试；参数错误、配额耗尽和不存在的地点不盲目重试。总截止时间传播到模型和工具调用，取消操作尽力中止下游请求，已发生的外部费用无法保证撤销。

对“只改第二天”的指令，模型返回限定范围的修改草稿，服务端应用到原版本并重新校验受影响路线。未授权修改的日期和固定地点由程序保护，不仅依靠 Prompt 要求保留。

## 6. 前后端协议与流式运行

### 6.1 建议 API

| 接口 | 用途 |
| --- | --- |
| `POST /api/v1/trips` | 创建旅行需求容器，返回 `trip_id` |
| `GET /api/v1/trips` | 行程列表 |
| `GET /api/v1/trips/{id}` | 当前需求及已保存行程 |
| `POST /api/v1/trips/{id}/runs:stream` | 发起生成或修改，以 SSE 事件格式返回运行过程 |
| `GET /api/v1/runs/{run_id}` | 获取运行状态、错误或最终版本引用 |
| `POST /api/v1/runs/{run_id}/cancel` | 请求取消仍在执行的运行 |
| `GET /api/v1/trips/{id}/revisions` | 获取版本列表 |
| `GET /api/v1/trips/{id}/revisions/{revision}` | 查看历史版本 |

运行请求携带 `client_request_id`、`base_revision`、操作类型和用户指令。服务端对同一行程的请求标识建立唯一约束；同一标识重复提交返回已有运行引用，正文不同则拒绝。首版每个行程最多一个活动运行，防止重复点击启动多个昂贵任务。

### 6.2 SSE 事件

前端用 `fetch` 发起 POST 并解析 `text/event-stream`，允许携带 JSON 请求体和取消信号；不依赖原生 EventSource 发 POST。解析器处理跨网络分块、心跳、错误和正常结束，不能假设一个 chunk 就是一条事件。FastAPI 可提供流式响应。[FastAPI SSE 文档](https://fastapi.tiangolo.com/tutorial/server-sent-events/)

事件统一包含 `run_id`、`seq`、`type`、`timestamp`、`payload`。建议类型为：

| 类型 | UI 行为 |
| --- | --- |
| `run.started` | 保存运行 ID，显示正在规划 |
| `stage.changed` | 显示查询地点、整理行程、校验路线等阶段 |
| `reasoning.delta` | 折叠展示模型思考过程；仅运行期推送，不持久化，断线后不补发 |
| `tool.started` / `tool.finished` | 展示简短进度，不泄露供应商密钥或原始敏感参数 |
| `message.delta` | 追加面向用户的说明文本 |
| `input.required` | 展示待补充信息并结束本轮 |
| `itinerary.committed` | 携带已保存版本引用，前端刷新行程数据 |
| `run.failed` / `run.cancelled` | 展示原因与后续操作 |
| `run.completed` | 结束运行，可能是行程完成或等待下一轮输入 |

流式说明、未完成的 JSON 和草稿不能直接覆盖已保存行程。前端收到提交事件后，以 API 中的持久化版本为准。模型推理内容只能作为 `reasoning.delta` 运行期过程事件展示：默认折叠、不持久化、不写入版本，断线恢复后不补发；正式回复仍以 `message.delta` 和最终持久化消息为准。

### 6.3 首版执行可靠性边界

首版运行绑定 HTTP 请求，在同一 API 进程内执行。客户端断连后尽力取消；进程重启后不自动恢复未完成的模型循环。运行使用状态与存活时间记录，启动清理或超时检查将遗留运行标记为 `interrupted`，用户可重新发起。

若已提交行程但最终 SSE 事件丢失，前端通过运行查询接口恢复最终展示。同一请求标识不会自动再次调用模型。首版不承诺 token 事件回放，也不通过自动重连重复执行生成请求。

将来需要离线继续时，将运行执行迁移到独立 Worker，API 只负责提交和订阅；再引入持久队列、事件重放和任务租约。`BackgroundTasks` 不作为持久任务队列的替代品。[FastAPI 背景任务说明](https://fastapi.tiangolo.com/tutorial/background-tasks/)

## 7. 数据模型与一致性

| 实体 | 主要内容 |
| --- | --- |
| `trips` | 标识、拥有者、规范化需求、当前版本、创建与更新时间 |
| `trip_revisions` | 行程 ID、版本号、父版本、结构化行程 JSONB、修改指令、来源运行 |
| `messages` | 行程 ID、角色、用户输入或最终说明、关联运行 |
| `runs` | 请求标识、输入、基础版本、状态、模型标识、耗时、调用用量、错误码 |
| `tool_executions` | 运行 ID、工具名、耗时、结果状态与脱敏摘要 |

初版行程根结构建议包含 `schema_version`、目的地、出行日期、人数、预算口径、每日活动、交通段、费用汇总、来源与警告。金额使用明确币种与精确数值表示，汇总由程序计算。天气、地点和价格估计保留 `source`、`fetched_at` 或 `estimated` 等可追溯信息。

**行程版本是业务事实，聊天消息是交互记录，Agent 内存是执行上下文。三者不能互相替代。** 长期用户偏好未来独立保存；不能把整段聊天历史当作永久偏好库。

保存修改时，在短事务中检查当前版本是否仍等于 `base_revision`，写新版本并更新版本指针和运行状态。版本发生冲突则返回冲突，由用户刷新后重试，不用最后写入者静默覆盖。长时间模型调用期间不持有数据库事务或行锁。

行程版本与对应运行成功状态在同一事务内提交，之后才发 SSE 成功事件。取消与提交竞争时也依据事务中的运行状态判定：已成功提交的运行不再改成已取消。

## 8. 旅行可信度与数据边界

模型输出的地点必须来自本次允许使用的候选集合，服务端根据供应商 POI ID 回填坐标和名称。为候选保存城市与来源，避免同名地点混淆。系统统一记录坐标系；高德地图坐标与其他数据源坐标混用前必须做转换。

地点存在不等于可访问：开放时间、预约和临时闭馆信息不足时标记待核实。预算是可解释估算，并非供应商报价；路线耗时包含交通方式和查询时间，适当增加步行、排队和换乘缓冲。硬约束无法满足时明确返回不可行项。

天气只使用数据源实际返回的有效日期范围。远期行程可保留室内替代选项，但不能把气候经验表述成当天预报。地图工具不可用时可以返回未核验草稿或失败原因，不能将降级结果标记为已核验正式行程。

## 9. RAG 与记忆的演进

首版依靠实时地点/路线和用户需求完成规划，不先建设知识平台。后续有稳定攻略来源时，优先在 PostgreSQL 增加 pgvector，复用已有数据库；它提供向量检索能力，中文分词、混合检索及排序仍需要额外设计。[pgvector 项目](https://github.com/pgvector/pgvector)

届时增加文档、片段、来源、城市、更新时间、Embedding 模型版本等字段，先验证检索相关性，再接到 `search_travel_knowledge` 工具。攻略可补充偏好与背景知识，实时天气和价格仍应查询对应数据源。

当出现“等待确认后继续”“预算与路线进入不同修复分支”等需求，再加入 LangGraph 外层编排。现有 Planner 可作为节点使用。持久 checkpointer 保存执行状态，业务表继续保存正式行程；引入图运行时不自动替代后台任务执行器。

对应关系为：原 `api/` 拆为 `routers/` 和 `schemas/`，`application/` 对应
`services/`，`domain/` 中的数据结构归入 `schemas/`、业务约束归入
`validators/`，外部供应商适配归入 `integrations/`，`persistence/` 拆为
`models/`、`crud/` 和 `config/`。这是本项目选择的命名约定，并非框架强制标准。

路由只处理协议与请求依赖，通过 Service 编排业务；CRUD 不返回 HTTP 响应，
也不自行提交事务。Service 明确事务边界，长时间模型和地图调用不占用数据库事务。
工具调用 Service 或 Client，避免在 Prompt、路由或工具定义中重复实现业务规则。

前端页面组合业务组件，路由集中在 `router/`；全局 Provider 在未来的入口
`src/main.tsx` 注册，可复用 Provider 按职责组织，不再单设 `app/`。
生成的 OpenAPI 类型放在 `api/`，`types/` 只存放额外的业务及视图类型。

后续实现应用时再添加 `backend/main.py`、前端入口和构建配置；部署阶段
再编写根目录 `compose.yaml`。当前可运行 Vite 前端开发服务，业务服务与容器编排尚未实现。

本地使用 Vite 开发服务代理 `/api` 到 FastAPI，PostgreSQL 在 Compose 中运行。部署时 Nginx 提供前端静态资源并代理 API，SSE 路径关闭缓冲、配置合适超时；首次部署只运行一个 API 执行实例，与请求内任务模型保持一致。

模型与地图服务凭证通过环境变量配置，不进入前端构建或 Git。公开部署前补充登录和资源归属检查、同源访问设置与配额限制；地图浏览器 key 按其平台规范限制使用范围。数据库使用持久卷并保留可恢复备份。

## 11. 开发顺序与验证标准

| 阶段 | 主要交付 | 验收重点 |
| --- | --- | --- |
| 0：独立 Agent 验证 | 输入输出与 State、工具及校验器、终端调用与样例评估 | 全国国内目的地解析，真实生成与局部修改通过检查后再接业务 |
| 1：契约与页面闭环 | 行程 Schema、API、模拟数据、React 工作台 | 表单 → 行程卡片 → 地图选择联动，前后端字段一致 |
| 2：真实规划接入 | 复用阶段 0 的 Planner、地点/天气工具与结构化结果 | 通过业务接口产生可追溯地点，错误可以解释 |
| 3：业务可靠性 | 路线与预算校验、有限修复、版本保存 | 未通过校验不提交，已有有效行程保留 |
| 4：交互完善 | SSE、取消、局部修改、历史版本 | 重复点击不重复执行，修改范围受控，断流能查询最终状态 |
| 5：部署与评估 | Compose、日志、固定请求集 | 测试可复现，能定位工具失败、超限和版本冲突 |

测试优先覆盖真正影响可靠性的行为：预算口径、候选 ID、局部修改保护、版本冲突、重复请求、取消与保存竞争、天气超范围和工具超时。后端用 pytest，前端对事件 reducer 做关键状态测试，再用 Playwright 验证“生成 → 展示 → 修改 → 保存”主流程。

准备约 10–20 条固定旅行请求用于起步回归，记录地点可追溯率、规则通过率、局部修改成功率、耗时和调用用量。这是小规模开发证据，不代表生产可靠性。模型输出质量与程序确定性测试分开评估，不依靠每次付费调用才能运行基础测试。

## 12. 当前决策与待实施时核验项

已确定的建议是：React/TypeScript 前端、FastAPI 模块化单体、LangChain 单 Planner、PostgreSQL、国内高德数据接入及请求内首版运行方式。它们与前一篇文档的“先完成小闭环，再按需扩展运行时”一致。

实施前需要核验：模型账户可用地域及工具能力、地图 key 与额度、预算默认口径，以及是否首版就需要多用户登录或断线继续运行。前两项影响真实 API 联调，后两项若改变，会调整鉴权和任务执行设计；不妨碍现在先按本文完成数据契约和模拟闭环。

本文通过 Context7 和已读取的官方文档核对关键能力，未安装依赖、未完成模型/地图性能测试。具体性能、成本和依赖版本以实际集成验证为准。
