# TripWeave 开发约定

本文件适用于 `tripweave/` 及其所有子目录。命令默认从 `tripweave/`
执行；Git 提交从父目录仓库根目录执行。

## 设计依据

- 不将目标架构、建议接口或文档中的验收方案描述为已经完成的功能。
- 技术方案以 `docs/01-architecture/02-system-architecture.md` 为基线；Agent 框架取舍见
  `docs/01-architecture/01-agent-framework-decision.md`；文档索引见 `docs/README.md`。
- 目标前端为 TypeScript + React + Vite，目标后端为 Python + FastAPI；
  Agent 首版采用 LangChain 单 Planner。依赖是否安装以项目配置和锁文件为准。
- 新增或调整架构时同步更新对应文档，区分已实现能力、目标设计和待验证假设。

## 目录与环境

- `backend/`：后端入口、接口、规划编排、领域规则、外部服务适配与数据访问。
- `frontend/`：前端页面、组件、地图联动与接口调用。
- `docs/`：正式架构、技术决策、设计与协议说明、前端样本数据。
- `tmp/`：本地校验报告、截图、日志、预览和中间产物，整个目录由 Git 忽略。
  前端按 `tmp/frontend/YYYY-MM-DD/<任务名>/` 分开保存不同校验的内容。
- `docs/README.md`：唯一文档总入口，README 不添加数字前缀，不在子目录重复建立。
- `docs/01-architecture/`：Agent 框架探索、系统方案与 `03-diagrams/` 架构图源文件。
- `docs/02-frontend/`：按 `01-planning/`、`02-design/`、`03-data/`、
  `04-features/` 分级存放实施计划、界面设计、数据契约与样本、功能说明。
  普通目录和文件按各层阅读顺序独立编号，新文档归入对应功能，避免重新平铺到 docs 根目录。
- `pyproject.toml`、`uv.lock`、`.python-version` 位于子项目根目录，
  由 uv 管理 Python 环境和依赖；保持 `[tool.uv] package = false`。
- 后端代码直接放在 `backend/`，不增加 `backend/app/`、Python 的 `src/`
  或再嵌套一层 `tripweave/`；前端使用 `frontend/src/`。
  应用所需的内部 Python 包按需添加 `__init__.py`。
- 已按架构建立目录骨架，空目录使用 `.gitkeep` 纳入版本管理，添加实际文件后
  可删除占位文件；新模块按需创建，不为当前规模增加抽象层。
- Python 依赖通过 `uv add`、`uv remove` 管理，前端初始化后使用 pnpm。
  依赖变更同步提交对应锁文件，不手工拼接锁文件内容。

## 模块职责

目录职责以 `docs/01-architecture/02-system-architecture.md` 第 10 节为准，后续实现遵循以下边界：

- `backend/config/`：应用配置、数据库连接和会话工厂。
- `backend/routers/`：参数校验、请求依赖、HTTP/SSE 协议及错误响应。
- `backend/schemas/`：Pydantic 请求、响应、行程、候选地点及运行事件模型。
- `backend/models/`：SQLAlchemy 表模型；`migrations/`：后续数据库迁移。
- `backend/crud/`：数据查询与写入，不处理 HTTP 响应或自行提交事务。
- `backend/services/`：需求合并、规划用例、运行控制、校验与版本保存；
  在用例层明确事务边界，长时间模型和地图调用不占用数据库事务。
- `backend/dependencies/`：数据库会话、身份校验等可复用请求依赖。
- `backend/agents/`：Planner、Prompt 和模型循环适配，不直接写数据库。
- `backend/tools/`：Agent 工具定义、参数与结果转换，复用 Service 和 Client。
- `backend/clients/`：模型、地图、天气供应商协议、外部请求、超时与错误转换。
- `backend/validators/`：预算、路线、地点与修改范围等纯业务校验。
- `backend/utils/`：日志、错误等通用工具，不堆放业务逻辑。
- `backend/tests/`：后端自动化测试与接口请求示例。
- 前端 `pages/` 组合页面，`components/` 放通用与业务组件，`router/` 管理
  路由，`api/` 放 API 客户端与生成类型，`hooks/` 放复用状态及事件处理，
  `types/` 放额外业务类型，`assets/`、`styles/`、`utils/` 按职责组织。
- 全局 Provider 在未来的 `frontend/src/main.tsx` 注册；前端不在多个状态
  容器重复维护同一份已保存行程。

## 简单优先与可读性

模块职责决定代码放在哪一层，本节约束实现的规模：分层正确不等于要改很多文件。

- 判断标准是"从上往下读一遍能不能跟上"：主要流程在一个函数里读完，
  辅助函数紧跟调用点；嵌套超过三层时用提前返回拆平，不为拆而拆。
- 先写直白实现，出现第二处真实重复再抽象。只有一个调用点时，不造接口、
  基类、工厂、注册表或插件机制；新增抽象要能指出它消除了哪几处重复。
- 一个功能尽量在 1–3 个文件内完成。改动跨 5 个及以上文件时，先确认是否是
  分层错位或接口设计问题；确实必须横跨时，在交付说明里写明原因。
- 不为"以后可能要"预留：未使用的参数、配置项、开关和扩展点不提前添加；
  确认出现第二处使用再加，事后补上比事后清理容易。
- 不把重构、重命名、格式化混进功能改动；纯搬移与纯格式化单独提交，便于审阅。
- 参数超过四个，或出现布尔开关控制分支时，先判断该拆函数还是换数据结构，
  不继续堆参数。
- 进度、日志和诊断能用一个回调和一行输出解决，就不新建事件总线或观察者层。
- 避免新增 `manager`、`helper`、`base_*` 这类无法判断职责的兜底命名；
  `utils/`、`common.py` 不继续堆放跨领域逻辑。
- 顺手发现但与本次目标无关的问题，记录到交付说明，不混入本次改动。
- 提交前自检：列清改了哪些文件、每个文件为什么必须改、能否少改一个。

## 命名与导入

- Python 文件、函数、参数和普通变量使用 `snake_case`，类使用
  `PascalCase`，真正的常量使用 `UPPER_SNAKE_CASE`。
- 函数名表达动作与业务对象，如 `get_trip_detail`；业务参数使用
  `trip_id`、`run_id`，避免遮蔽 `id`、`list` 等内置名称。
- Python 函数补齐有意义的参数与返回类型，可空类型使用 `str | None`。
- Python 导入按标准库、第三方、项目模块分组，内部导入与实际目录和启动方式
  一致；不使用不存在的 `tripweave.tripweave` 或参考项目的包路径。
- 同一业务跨层沿用一致名称；同名模块通过职责别名区分。
- TypeScript 使用严格类型检查；变量、函数使用 `camelCase`，组件与类型
  使用 `PascalCase`，组件文件命名与导出保持一致，避免无理由的 `any`。
- 对外 JSON 字段和事件名称以协议为准，不因内部重命名擅自改变。

## 接口、数据与外部调用

- 修改已有行为时保持 URL、HTTP 方法、请求参数、响应字段和 SSE 事件兼容；
  确需调整时同步修改前端、文档和相关验证。
- 响应通过明确的数据模型定义；业务失败与系统异常分开处理，使用恰当的
  HTTP 状态码，不将异常静默转换成成功结果。
- 数据库模型与迁移对应实际结构；异步调用必须 `await`，避免阻塞事件循环。
- 行程版本与运行状态按设计保持一致；流式草稿不能覆盖已保存的有效行程。
- 地点、天气、路线和价格注明来源及适用范围，区分查询结果、估计和未知信息。
- 外部模型与地图调用配置超时、重试和调用预算；单元测试使用替身，
  真实外部调用仅在明确需要的集成验证中执行。
- 密钥、令牌、真实 `.env` 不得提交或写入日志；通过环境变量读取配置，
  只提交无真实凭据的 `.env.example` 等模板。后端密钥不得进入前端代码或产物。

## 注释与文档字符串

- 注释、文档字符串和项目文档使用简体中文，说明用途、业务约束与必要原因，
  不逐行重复直观代码；修改代码时同步更新相关说明。
- 公共函数、异步函数、接口处理函数与方法使用三引号文档字符串；类用简短
  文档字符串说明职责。
- 多行文档字符串的起始与结束三引号各占一行，摘要以句号结尾；参数或返回值
  需要额外说明时，空一行后使用 `:param 参数名:`、`:return:` 和
  `:raises 异常类型:`，不重复类型注解即可表达的信息。
- 事务、并发、版本冲突、取消和外部接口约束，在相关逻辑附近解释原因。

## 验证与交付

- 当前可执行的环境检查为 `uv sync --offline`；缓存不足时使用 `uv sync`。
- 前端在 `frontend/` 执行 `pnpm dev`，静态检查为 `pnpm typecheck`、`pnpm lint`。
  后端尚未配置应用启动、测试与静态检查工具，不声称其已经通过。
- 引入 Ruff、pytest 或前端检查工具后，运行与变更相关的检查；
  修改业务行为时覆盖关键边界、异常和接口契约，不编写仅重复实现细节的测试。
- 重命名同步修改导入、调用、测试与文档；调整依赖后验证环境同步。
- 校验结果和过程产物只写入 `tmp/` 下对应任务的子目录，不写入 `docs/`
  或项目根目录，也不另建 `.oil-ui/` 等过程目录。`docs/` 可说明验证方法与
  功能边界，不堆放逐轮测试结果、截图、日志或生成工具的校验回执。
- 父目录 `.gitignore` 管理系统和编辑器临时文件，子项目 `.gitignore`
  管理虚拟环境、依赖、构建产物、缓存、日志及本地配置。
- 保留源码、文档、配置模板、`uv.lock`、前端锁文件和可共享的编辑器设置。
- 提交前检查暂存区内容与差异，确认不包含凭据、依赖目录或临时产物；
  交付说明真实列出修改内容、验证结果与尚未完成的事项。

## Git 提交规范

- 按用户约定，提交标题统一使用 `feat(子项目文件夹名称): 中文描述说明`。
  本子项目的 scope 固定为 `tripweave`，不使用父仓库名或内部模块名。
- 使用半角括号、半角冒号，冒号后加一个空格；描述使用简体中文、以动词开头，
  不超过 50 个字符，结尾不加句号，并准确概括本次实际变更。
- 示例：`feat(tripweave): 完善项目配置与开发约定`。
- 即使本次只涉及修复、文档或配置，也按本项目约定使用上述标题格式。
- 需要正文时，标题后空一行，说明背景与实现思路，每行不超过 72 字符。
  仅在确有关联任务或破坏性变更时添加关联信息或 `BREAKING CHANGE:` 说明。
- 一个提交聚焦同一子项目；父目录为其提供的公共配置可随本次提交一并纳入。
  提交其他子项目时使用对应文件夹名称作为 scope。
