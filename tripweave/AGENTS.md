# 开发规范

适用于本仓库及所有子目录。以下是通用的代码编写与风格规范；目录示例只用于说明职责划分，不要求照搬名称或层数。

## 核心原则

- **可读性优先**：代码首先是给人读的。优先让主流程清晰、命名准确、控制流简单。
- **简洁优先**：简洁不是少写代码，而是减少不必要的复杂度。不要为了“看起来完整”而过度设计，也不要把简单功能拆得支离破碎。
- **一致优先**：遵循仓库已有的语言习惯、目录职责、文档和测试方式；新增代码应与周边代码保持一致。
- **结果可验证**：改动应能通过格式化、静态检查、类型检查和测试；无法验证的部分要明确说明。

## 结构与命名

- 按职责组织代码，而不是按文件类型机械分层。
- 一个模块应承担清晰、单一的职责；入口、业务编排、数据契约、外部适配、异常定义和测试各自内聚。
- 名称要说明用途和意图，避免无意义缩写、编号，以及 `Manager`、`Util`、`Helper` 这类空泛后缀。
- 不提前创建空目录、占位模块，或只为“以后可能用到”的抽象。
- 同一功能的相关代码尽量放在相邻位置；需要跨层时，调用关系应能一眼看清。

示例（仅说明职责划分，不要求使用相同目录名）：

```text
project/
  api/            # 对外接口与路由
  services/       # 业务流程编排
  models/         # 数据结构与契约
  integrations/   # 外部服务适配
  errors/         # 异常定义
  tests/          # 自动化测试
```

小型功能可以合并到更少的文件；不要为了凑齐分层而创建只做转发的空壳模块。

## 简洁优先

简洁优先的目标是降低阅读和维护成本，不是机械追求文件数量少。

应该拆分的情况：

- 职责明显不同，混在一起会让主流程难以阅读。
- 出现真实的重复逻辑，且抽象后能减少重复，而不是增加间接层。
- 某段逻辑复杂到需要独立测试，或需要隔离外部依赖。
- 外部服务、数据转换、错误映射等边界需要独立维护。

不应该拆分的情况：

- 只有一个调用点，拆出去只是多一次跳转。
- 只是把一段代码原样搬到另一个文件，没有形成更清晰的职责。
- 为了套用某种架构而增加 base、manager、factory、registry 或空接口。
- 一个功能被分散到十几个文件，读代码时要在文件间反复跳转。

判断标准是：拆分后是否更容易理解和修改。主流程应尽量能在一个函数或一个模块中自上而下读完；辅助逻辑放在紧邻调用点或明确的边界模块中。不要为一个调用点添加参数、开关、基类或扩展点。

## 代码风格

- 遵循项目的格式化、静态检查和类型检查配置，不手工对抗工具。
- 优先早返回，减少多层嵌套；单个函数保持单一目的。
- 避免魔法数字和重复字符串；需要时提取有名字的常量。
- 删除无用代码、调试输出和多余兼容垫片，不保留“以后可能用”的分支。
- 优先使用语言标准库、框架已有能力和项目现有依赖，不重复造轮子。

## 注释与文档

- 注释、文档字符串和项目文档使用简体中文；标识符遵循所用语言的命名惯例。
- 类、函数和方法都要有简短的文档字符串，说明它做什么、什么时候使用；不要只复述名称。
- 参数要说明含义、单位、取值范围或约束；无参数时可省略参数说明。返回值、异常和副作用在不明显时也要说明。
- 文档字符串沿用现有 reST 风格（概要 + `:param` / `:return` / `:raises`），并与代码保持同步。
- 对不直观的业务规则、边界条件、兼容性处理、算法步骤或容易误改的地方，添加必要的 `#` 注释，解释“为什么”而不是“做了什么”。
- 不写复述代码的注释，不保留过期注释、被注释掉的旧代码或没有信息量的分隔线。

示例：

```python
def load_config(path: Path) -> Config:
    """
    读取并校验配置文件。

    :param path: 配置文件路径。
    :return: 通过结构校验的配置对象。
    :raises ValueError: 文件内容不符合配置结构时抛出。
    """
```

## 错误与数据边界

- 在系统边界校验输入；内部代码信任已校验的数据，不重复做无意义的防御。
- 异常类型集中定义；在边界处转换为对外错误，内部保留原始类型、失败阶段和必要上下文。
- 不静默吞掉异常；无法恢复时要记录可诊断的信息，对外消息要脱敏。
- 外部调用要设置超时，限制并发、重试和资源占用。
- 不伪造外部事实。来源、单位、坐标系、采集时间等上下文必须随数据保留，不得混用或擅自转换。
- 未知值要显式表达，不能用 0、空字符串或默认值冒充已查询到的结果。
- 模型或外部服务只能引用程序提供的事实标识，不得从摘要、自然语言或推断中补全坐标、价格等关键事实。
- 密钥只从环境变量读取；不写入源码、文档、日志、前端或提交记录。
- 只展示服务实际返回的信息，不伪造推理、进度或调用结果。
- 命令行工具将结果与过程日志分离：结果写标准输出，进度和诊断写标准错误，并用退出码表达成功或失败。

## 测试与验证

- 自动测试默认使用替身隔离网络、数据库和第三方服务；真实服务调用必须获得明确授权，并确认调用范围。
- 测试覆盖成功路径、失败路径和关键边界，不只验证“能跑通”。
- 交付前运行仓库已配置的格式化、静态检查、类型检查和测试命令；具体命令见 README 和 docs。
- 如实区分替身测试、真实服务验证和未完成部分，不把未验证的能力描述为已实现。
- 不通过跳过钩子、关闭检查或删除测试来让结果变绿。

## 依赖与交付

- 使用仓库已有的包管理器和锁文件；依赖变更后同步更新锁文件，不手改锁文件内容。
- 不引入只为单个调用点服务的框架、基类或注册表；新增依赖应有明确收益。
- 不自动提交 Git；用户要求提交时，遵循仓库既有的提交信息格式（本项目使用简体中文 Conventional Commits）。
- 纯整理与功能变更分开提交；重命名时同步修改导入、调用、示例、测试和文档。
