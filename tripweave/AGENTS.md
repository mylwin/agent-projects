# TripWeave 开发约定

本文件适用于 `tripweave/` 及其所有子目录。命令默认从 `tripweave/`
执行；Git 提交从父目录仓库根目录执行。

## 项目状态与设计依据

- 当前为项目配置与架构设计阶段，`backend/`、`frontend/` 尚未实现应用。
  不将目标架构、建议接口或文档中的验收方案描述为已经完成的功能。
- 技术方案以 `docs/architecture.md` 为基线；Agent 框架取舍见
  `docs/agent-framework-decision.md`；文档索引见 `docs/README.md`。
- 目标前端为 TypeScript + React + Vite，目标后端为 Python + FastAPI；
  Agent 首版采用 LangChain 单 Planner。依赖是否安装以项目配置和锁文件为准。
- 新增或调整架构时同步更新对应文档，区分已实现能力、目标设计和待验证假设。

## 目录与环境

- `backend/`：后端入口、接口、规划编排、领域规则、外部服务适配与数据访问。
- `frontend/`：前端页面、组件、地图联动与接口调用。
- `docs/`：架构、技术决策、协议说明及验证记录。
- `docs/architecture/`：交互架构图、图定义及配套生成和检查记录。
- `pyproject.toml`、`uv.lock`、`.python-version` 位于子项目根目录，
  由 uv 管理 Python 环境和依赖；保持 `[tool.uv] package = false`。
- 使用现有目录，不增加 `src/` 或再嵌套一层 `tripweave/`。
  应用所需的内部 Python 包按需添加 `__init__.py`。
- 只在需要时创建模块，不预建空文件或通用工具目录，不为当前规模增加抽象层。
- Python 依赖通过 `uv add`、`uv remove` 管理，前端初始化后使用 pnpm。
  依赖变更同步提交对应锁文件，不手工拼接锁文件内容。

## 模块职责

以下为后端逐步实现时的职责边界，不要求一次性建立全部目录。

- API 层负责参数校验、依赖注入、HTTP/SSE 协议及错误响应。
- 应用服务负责需求合并、调用 Planner、触发校验和保存行程。
- Planner 负责工具调用与结构化草稿，不直接写数据库或绕过业务校验。
- 工具与供应商适配负责参数约束、外部请求、超时和错误转换。
- 领域服务负责地点规范化、路线核验、预算汇总及行程约束校验。
- 仓储层负责查询、事务和版本更新，不执行模型循环；事务边界在用例层明确。
- 前端组件负责展示与交互；接口调用、地图适配及运行事件处理按职责组织，
  不在多个状态容器重复维护同一份已保存行程。

## 命名与导入

- Python 文件、函数、参数和普通变量使用 `snake_case`，类使用
  `PascalCase`，真正的常量使用 `UPPER_SNAKE_CASE`。
- 函数名表达动作与业务对象，如 `get_trip_detail`；业务参数使用
  `trip_id`、`run_id`，避免遮蔽 `id`、`list` 等内置名称。
- Python 函数补齐有意义的参数与返回类型，可空类型使用 `str | None`。
- Python 导入按标准库、第三方、项目模块分组，内部导入与实际目录和启动方式
  一致；不使用不存在的 `tripweave.tripweave` 或参考项目的包路径。
- 同一业务跨层沿用一致名称；同名模块通过职责别名区分。
- TypeScript 使用严格类型检查；变量、函数使用 `camelCase`，组件与类型
  使用 `PascalCase`，组件文件命名与导出保持一致，避免无理由的 `any`。
- 对外 JSON 字段和事件名称以协议为准，不因内部重命名擅自改变。

## 接口、数据与外部调用

- 修改已有行为时保持 URL、HTTP 方法、请求参数、响应字段和 SSE 事件兼容；
  确需调整时同步修改前端、文档和相关验证。
- 响应通过明确的数据模型定义；业务失败与系统异常分开处理，使用恰当的
  HTTP 状态码，不将异常静默转换成成功结果。
- 数据库模型与迁移对应实际结构；异步调用必须 `await`，避免阻塞事件循环。
- 行程版本与运行状态按设计保持一致；流式草稿不能覆盖已保存的有效行程。
- 地点、天气、路线和价格注明来源及适用范围，区分查询结果、估计和未知信息。
- 外部模型与地图调用配置超时、重试和调用预算；单元测试使用替身，
  真实外部调用仅在明确需要的集成验证中执行。
- 密钥、令牌、真实 `.env` 不得提交或写入日志；通过环境变量读取配置，
  只提交无真实凭据的 `.env.example` 等模板。后端密钥不得进入前端代码或产物。

## 注释与文档字符串

- 注释、文档字符串和项目文档使用简体中文，说明用途、业务约束与必要原因，
  不逐行重复直观代码；修改代码时同步更新相关说明。
- 公共函数、异步函数、接口处理函数与方法使用三引号文档字符串；类用简短
  文档字符串说明职责。
- 多行文档字符串的起始与结束三引号各占一行，摘要以句号结尾；参数或返回值
  需要额外说明时，空一行后使用 `:param 参数名:`、`:return:` 和
  `:raises 异常类型:`，不重复类型注解即可表达的信息。
- 事务、并发、版本冲突、取消和外部接口约束，在相关逻辑附近解释原因。

## 验证与交付

- 当前可执行的环境检查为 `uv sync --offline`；缓存不足时使用 `uv sync`。
- 目前未配置应用启动命令、测试与静态检查工具；不要声称其已经通过。
  实现相关能力时同步补充 README 中的实际命令。
- 引入 Ruff、pytest 或前端检查工具后，运行与变更相关的检查；
  修改业务行为时覆盖关键边界、异常和接口契约，不编写仅重复实现细节的测试。
- 重命名同步修改导入、调用、测试与文档；调整依赖后验证环境同步。
- 父目录 `.gitignore` 管理系统和编辑器临时文件，子项目 `.gitignore`
  管理虚拟环境、依赖、构建产物、缓存、日志及本地配置。
- 保留源码、文档、配置模板、`uv.lock`、前端锁文件和可共享的编辑器设置。
- 提交前检查暂存区内容与差异，确认不包含凭据、依赖目录或临时产物；
  交付说明真实列出修改内容、验证结果与尚未完成的事项。

## Git 提交规范

- 按用户约定，提交标题统一使用 `feat(子项目文件夹名称): 中文描述说明`。
  本子项目的 scope 固定为 `tripweave`，不使用父仓库名或内部模块名。
- 使用半角括号、半角冒号，冒号后加一个空格；描述使用简体中文、以动词开头，
  不超过 50 个字符，结尾不加句号，并准确概括本次实际变更。
- 示例：`feat(tripweave): 完善项目配置与开发约定`。
- 即使本次只涉及修复、文档或配置，也按本项目约定使用上述标题格式。
- 需要正文时，标题后空一行，说明背景与实现思路，每行不超过 72 字符。
  仅在确有关联任务或破坏性变更时添加关联信息或 `BREAKING CHANGE:` 说明。
- 一个提交聚焦同一子项目；父目录为其提供的公共配置可随本次提交一并纳入。
  提交其他子项目时使用对应文件夹名称作为 scope。
